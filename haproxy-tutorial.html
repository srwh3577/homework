1. 什麼是 HAProxy？

HAProxy（High Availability Proxy）是一套以 C 語言寫成的 高效能 TCP/HTTP 負載平衡器與反向代理。它能把湧入的流量公平地分發到多台後端伺服器，並在某台伺服器故障時自動排除它—— 所以一台普通伺服器扛不住的流量、單機故障就服務中斷的問題，到了 HAProxy 面前都能迎刃而解。

沒有 vs 有負載平衡器

❌ 沒有 LB：單點故障 + 瓶頸

graph LR C1["Client A"] --> S["Web Server
(唯一一台)"] C2["Client B"] --> S C3["Client C"] --> S

流量、可用性全壓在一台機器上。它一掛，整個服務都掛。

✅ 有 HAProxy：分流 + 容錯

graph LR C1["Client A"] --> HA["HAProxy"] C2["Client B"] --> HA C3["Client C"] --> HA HA --> S1["Web 1"] HA --> S2["Web 2"] HA --> S3["Web 3"]

流量被分散到多台 Web；任一台掛了，HAProxy 自動把它跳過。

HAProxy 提供的核心能力：

  • 負載平衡：把流量依各種策略（輪詢、最少連線、來源 IP hash……）分發到多台後端。
  • 高可用：透過健康檢查自動排除故障節點；自身可雙機熱備（Keepalived）。
  • 反向代理：對外只露一個入口，後端伺服器藏在內網，安全且彈性。
  • SSL Termination：在 LB 統一處理 HTTPS 加解密，減輕後端負擔。
  • 內容路由：依 URL、Host、Cookie 等規則把請求送到不同 backend。

4. TCP（L4）vs HTTP（L7）模式

HAProxy 可工作在 OSI 第 4 層（TCP）或第 7 層（HTTP），這是兩種完全不同的能力光譜。

mode tcp（Layer 4）

graph LR C["Client"] -->|"TCP 位元組"| HA["HAProxy
L4 mode
只看 IP + Port"] HA -->|"原樣轉發"| S["Backend"]
  • 不解析應用層內容，極快。
  • 適合任何 TCP 服務：MySQL、Redis、SMTP、純 TCP。
  • 無法依 URL/Header 路由。

mode http（Layer 7）

graph LR C["Client"] -->|"HTTP request"| HA["HAProxy
L7 mode
解析 HTTP"] HA -->|"可依 URL/Header 路由
可改寫 Header"| S["Backend"]
  • 解析 HTTP，可看 URL、Method、Header、Cookie。
  • 支援 ACL 內容路由、Header 改寫、HTTP/2、HTTPS 卸載。
  • 稍慢，但 Web 場景幾乎一定用這個。
實務原則：HTTP/HTTPS 服務一律用 mode http；其他協定（資料庫、訊息佇列）用 mode tcp。

圖 6-1　依請求特性選擇演算法的決策樹
演算法說明適用
roundrobin輪流分配，支援動態調整 weight無狀態、處理時間平均的請求（預設選擇）
static-rr靜態輪詢，weight 不可動態改跟 roundrobin 類似但更快
leastconn送給「目前連線數最少」的 server長連線、處理時間差異大（LDAP、SQL、WebSocket）
source依 source IP hash需要「同 IP → 同 server」的簡單黏滯
uri依 URI hash（HTTP only）後端有快取，希望「同 URL → 同 server」提高命中率
url_param / hdr(name)依某 URL 參數或 Header hash已用 token / userId 做識別
first一律先送第一台，第一台滿了才送下一台節能、彈性縮放（讓多餘 server 閒置）
用 source 的陷阱：若所有客戶端都從同一個 NAT 出口（例如公司、行動網路）來， hash 後會擠到同一台 server，負載完全不均。考慮改用 cookie-based sticky（第 10 節）。

7. 健康檢查（Health Check）

在 server 設定後面加 check，HAProxy 就會定期探測這台後端是否還活著。 探測連續失敗 fall 次標記為 DOWN，連續成功 rise 次標記為 UP。DOWN 的 server 不再收新流量。

stateDiagram-v2 Up: 健康 UP（接收流量） Down: 故障 DOWN（不分配新請求） [*] --> Up Up --> Down: 連續失敗 fall 次 Down --> Up: 連續成功 rise 次
圖 7-1　健康檢查的狀態機：來回切換由 fall/rise 控制，避免抖動
backend web_servers
    option httpchk GET /health         # 用 HTTP GET /health 當健康檢查
    http-check expect status 200      # 預期回 200 才算 UP
    default-server inter 3s fall 3 rise 2  # 每 3s 檢查；3 次失敗算掛；2 次成功復活
    server web1 10.0.0.11:8080 check
    server web2 10.0.0.12:8080 check
    server web3 10.0.0.13:8080 check backup   # backup：全死才啟用

視覺化 server 池狀態

web110.0.0.11:8080 · weight 100UP
web210.0.0.12:8080 · weight 100UP
web310.0.0.13:8080 · 連 3 次健康檢查失敗DOWN

↑ web3 DOWN，新請求自動只分配給 web1 / web2，零中斷

專用健康檢查端點：後端應提供 /health（或 /ping）這類輕量端點—— 回 200 = OK，500 = 我有問題，請別再給我流量。避免用首頁這種重邏輯當檢查目標。

8. 設定檔結構與完整範例動手做

HAProxy 設定檔（通常 /etc/haproxy/haproxy.cfg）由幾個區段組成：

區段作用
global進程級設定：log、user、maxconn、SSL 預設等。整份檔案只有一個。
defaults後續所有 frontend / backend / listen 共用的預設值（mode、timeout、option…）。
frontend監聽 + ACL + 路由規則。
backendserver 池 + balance + 健康檢查。
listenfrontend + backend 的合體簡寫。

一份完整的入門設定：HTTP 平衡到 3 台後端

global
    log /dev/log local0
    maxconn 50000
    user haproxy
    group haproxy
    daemon

defaults
    mode http
    log global
    option httplog
    option dontlognull          # 不記錄空連線（健康檢查噪音）
    option forwardfor           # 加 X-Forwarded-For，讓後端看到真實 client IP
    timeout connect 5s
    timeout client  30s
    timeout server  30s

frontend http_in
    bind *:80
    default_backend web_servers

backend web_servers
    balance roundrobin
    option httpchk GET /health
    server web1 10.0.0.11:8080 check
    server web2 10.0.0.12:8080 check
    server web3 10.0.0.13:8080 check backup

啟動與重載

# 檢查語法（改設定後一定要先驗證）
haproxy -c -f /etc/haproxy/haproxy.cfg

# 啟動 / 重啟 / 平滑重載（推薦：不中斷既有連線）
systemctl start haproxy
systemctl reload haproxy
用 reload，不要用 restart：reload 會優雅地把舊進程留著處理現存連線，新連線交給新進程，幾乎零中斷。restart 會殺斷所有連線。

9. ACL 與內容路由

ACL（Access Control List） 是 HAProxy 的條件規則語法。它能取得請求的任意屬性（URL 路徑、Host、來源 IP、Cookie……）， 然後讓 use_backend、http-request deny、http-request redirect 等指令依條件決策。

flowchart LR R["請求
Host + Path"] --> FE["Frontend"] FE -->|"path 以 /api/ 開頭"| BE_API["backend api_servers"] FE -->|"path 以 /static/ 開頭"| BE_STATIC["backend static_servers"] FE -->|"Host = admin.example.com"| BE_ADMIN["backend admin_servers"] FE -->|"以上都不符合"| BE_WEB["default_backend web_servers"] style FE fill:#e0f2ef,stroke:#0e8674 style BE_API fill:#fcefe2,stroke:#e07b2b style BE_STATIC fill:#fcefe2,stroke:#e07b2b style BE_ADMIN fill:#fcefe2,stroke:#e07b2b
圖 9-1　依 Host / Path 把同一個入口的流量送到不同 backend
frontend http_in
    bind *:80

    # 定義 ACL（給條件取個名字）
    acl is_api    path_beg /api/
    acl is_static path_beg /static/
    acl is_admin  hdr(host) -i admin.example.com
    acl is_intern src 10.0.0.0/8

    # 依條件路由（從上而下，第一個匹配就採用）
    use_backend api_servers    if is_api
    use_backend static_servers if is_static
    use_backend admin_servers  if is_admin is_intern   # 同時成立才採用

    # 都不匹配時的兜底
    default_backend web_servers

    # 封鎖某些 ACL
    http-request deny if !is_intern is_admin   # 外部不准進 admin
常用取值意義
path, path_beg, path_end完整路徑 / 開頭符合 / 結尾符合
hdr(name)取某個 Header 的值（如 hdr(host)）
src來源 IP（可比對 CIDR）
methodHTTP method（GET / POST...）
url_param(name)取某 URL 參數
ssl_fc當前連線是否為 SSL/HTTPS
順序很重要：use_backend 由上而下逐條評估，第一個匹配的就生效， 其餘不再判斷。把較具體的規則放前面，泛用的放後面。

10. Session 黏滯（Sticky）

有些應用把 session 存在單台後端的記憶體裡（例如沒共用 Redis 的 PHP/Java 應用）。 這時候同一個使用者每次都得回到同一台 server，否則他就會「莫名其妙登出」。這就是 sticky session 要解決的問題。 最常用且最可靠的方式是 Cookie based：

sequenceDiagram participant C as Client participant H as HAProxy participant W1 as web1 C->>H: 1. 首次請求（無 Cookie） H->>W1: 2. 依演算法挑到 web1 W1-->>H: 3. 回應內容 H-->>C: 4. 回應 + Set-Cookie: SERVERID=web1 Note over C,W1: 之後同一個瀏覽器一定帶這個 Cookie C->>H: 5. 後續請求（Cookie: SERVERID=web1） H->>W1: 6. 直接送 web1，跳過演算法 W1-->>H: 7. 回應 H-->>C: 8. 回應
圖 10-1　Cookie sticky：第一次請求被演算法分配，之後永遠回到同一台
backend web_servers
    balance roundrobin
    cookie SERVERID insert indirect nocache    # 由 HAProxy 植入 Cookie
    server web1 10.0.0.11:8080 check cookie web1
    server web2 10.0.0.12:8080 check cookie web2
    server web3 10.0.0.13:8080 check cookie web3
更好的長遠方案：讓 session 不要放單機記憶體，改放共用的 Redis/DB，這樣任何一台 server 都能服務任何使用者，徹底擺脫黏滯需求。 sticky 是不得已的折衷——它讓擴容、故障切換都變得不對稱。

11. SSL/TLS Termination

把 HTTPS 的加解密集中在 HAProxy 處理、後端內網仍跑明文 HTTP，就是 SSL Termination。 好處：憑證只需放一處、CPU 加解密集中、後端設定大幅簡化。

graph LR C["客戶端
瀏覽器"] -->|"HTTPS (加密)"| HA["HAProxy
解 TLS"] HA -->|"HTTP 明文
(內網)"| S1["web1"] HA -->|"HTTP 明文
(內網)"| S2["web2"] style HA fill:#e0f2ef,stroke:#0e8674
圖 11-1　外網吃 HTTPS、內網跑 HTTP；憑證只在 HAProxy 上
frontend https_in
    # 注意 pem 檔需包含「憑證 + 私鑰」一起
    bind *:443 ssl crt /etc/haproxy/certs/site.pem
    bind *:80

    # 強制把 HTTP 轉成 HTTPS
    http-request redirect scheme https code 301 unless { ssl_fc }

    default_backend web_servers

backend web_servers
    balance roundrobin
    http-request set-header X-Forwarded-Proto https if { ssl_fc }
    server web1 10.0.0.11:8080 check
    server web2 10.0.0.12:8080 check
需要端對端加密？那就要 SSL Passthrough（mode tcp 直接轉發加密流量，HAProxy 不解密）， 或在 server 行加 ssl verify none 做SSL re-encryption（HAProxy 解了再用 HTTPS 連後端）。安全性要求高的環境會選後者。

12. 高可用：HAProxy + Keepalived

HAProxy 解決了「後端高可用」，但是它自己也可能掛掉。標準解法是部署兩台 HAProxy（Master + Backup）， 由 Keepalived 透過 VRRP 協定共享一個虛擬 IP（VIP）。Master 掛了，Backup 自動接管 VIP，秒級切換。

10.0.0.12

圖 12-1　兩台 HAProxy 共用一個 VIP；Master 故障時 Backup 透過 VRRP 接管
# /etc/keepalived/keepalived.conf （Master 機）
vrrp_script chk_haproxy {
    script "killall -0 haproxy"     # 檢查 haproxy 程序是否活著
    interval 2
    weight 2
}

vrrp_instance VI_1 {
    state MASTER
    interface eth0
    virtual_router_id 51
    priority 110                   # Master 較高
    advert_int 1
    authentication { auth_type PASS  auth_pass mysecret }
    virtual_ipaddress { 10.0.0.100/24 }
    track_script { chk_haproxy }
}

Backup 機把 state 改成 BACKUP、priority 降低（例如 100）即可。

13. Stats 頁面與監控必開

HAProxy 內建一個漂亮的 stats 頁面，能即時看每個 frontend/backend/server 的狀態、連線數、流量、健康檢查結果——上線前一定要打開：

listen stats
    bind *:8404
    mode http
    stats enable
    stats uri /stats
    stats refresh 5s
    stats auth admin:secretPassword       # 基本驗證
    stats hide-version

之後用瀏覽器開 http://your-haproxy:8404/stats，輸入帳密就能看到完整狀態表。

  • 每個 server 一行：UP/DOWN、目前連線、累計請求、回應碼分佈。
  • 可直接在頁面上暫停某台 server（drain）做維護，不必改設定檔。
  • 進階監控可整合 Prometheus exporter（HAProxy 2.0+ 內建）→ Grafana 儀表板。
安全提醒：stats 頁面含敏感資訊（後端 IP、連線、URL），務必用 stats auth 加密碼， 或只 bind 到內網介面，絕不可暴露到公網。

14. 最佳實踐與常見陷阱

✅ 最佳實踐

  • 所有 backend 都設健康檢查，後端做專用 /health 端點。
  • 改設定後用 haproxy -c -f cfg 驗證語法，再 reload。
  • 用 reload 而非 restart，做到零中斷切換。
  • 開 option forwardfor，讓後端拿得到真實 client IP。
  • 合理設定 timeout connect/client/server，避免連線卡死。
  • SSL 集中在 HAProxy 處理，憑證一處管理。
  • 必開 stats 頁面 + 整合 Prometheus 監控。
  • 對外只用兩台 HAProxy + Keepalived，消除單點。

⚠️ 常見陷阱

  • 沒寫健康檢查，故障 server 仍接流量 → 大量 5xx。
  • 用 source 演算法卻所有 client 來自 NAT，流量擠到一台。
  • ACL 順序錯：泛用規則放前面，具體規則永遠不會匹配。
  • timeout server 比後端業務還短，請求被誤殺成 504。
  • Sticky 用 source + NAT，負載完全失衡。
  • SSL pem 檔權限不對、憑證 + 私鑰沒合在一起 → 啟動失敗。
  • maxconn 設太低，吞吐被自己卡住（記得也調 OS 的 ulimit）。
  • 用 restart 代替 reload，現存連線全被殺。
  • stats 頁面忘了加密碼，後端結構外洩。
