1. 什麼是 Kafka？

Apache Kafka 是一個分散式事件串流平台（Distributed Event Streaming Platform）。 最初由 LinkedIn 開發、2011 年開源，現為 Apache 頂級專案。你可以把它想成一條 超高吞吐、可持久化、可重播的「資料管道」：上游系統把事件不斷寫進去，下游系統各自照自己的步調讀出來。

Kafka 同時具備三種能力：

  • 發布／訂閱（Pub/Sub）：像訊息佇列一樣，發布者送訊息、訂閱者收訊息。
  • 持久化儲存：訊息寫到磁碟並可保留數天到永久，不是讀完就消失。
  • 串流處理：可即時對資料流做轉換、聚合（搭配 Kafka Streams／ksqlDB）。

典型使用場景：

  • 微服務之間的非同步解耦（訂單、金流、庫存、通知各自獨立）
  • 日誌與指標收集（把各機器的 log 集中後送往分析系統）
  • 使用者行為追蹤（點擊、瀏覽事件即時匯流）
  • 資料管線（ETL）與資料庫變更擷取（CDC）
  • 即時運算（風控、推薦、監控告警）
一句話理解：傳統訊息佇列「讀完即丟」，Kafka 則是一份「可重複讀取的事件日誌（log）」—— 訊息被讀取後仍然留著，多個下游可各自從不同位置讀，甚至可以倒帶重讀。

2. 為什麼需要 Kafka？

想像一個電商系統：當「訂單服務」產生一筆新訂單時，庫存服務要扣庫存、通知服務要寄信、 分析服務要記錄。如果讓訂單服務直接呼叫每一個下游服務，會發生什麼？

問題：點對點直連造成 N×M 的耦合

graph LR A1["訂單服務"] --> B1["庫存服務"] A1 --> B2["通知服務"] A1 --> B3["分析服務"] A2["金流服務"] --> B1 A2 --> B2 A2 --> B3
圖 2-1　每新增一個上游或下游，連線數量爆炸成長，且彼此緊密相依

這種設計的痛點：

  • 下游服務一掛，上游就被拖累（同步呼叫塞住、逾時）。
  • 每多一個消費端，上游都得改程式加一條呼叫。
  • 流量尖峰時，上游直接把下游打垮，缺乏緩衝。

解法：用 Kafka 當中間的「緩衝與廣播層」

graph LR A1["訂單服務"] -->|發布事件| K[("Kafka")] A2["金流服務"] -->|發布事件| K K -->|訂閱| B1["庫存服務"] K -->|訂閱| B2["通知服務"] K -->|訂閱| B3["分析服務"]
圖 2-2　上游只管把事件丟進 Kafka，下游各自訂閱，彼此完全解耦

引入 Kafka 後：

  • 解耦：上游不需要知道有誰在消費；新增下游只要訂閱即可，上游零改動。
  • 削峰填谷：尖峰流量先堆在 Kafka，下游按自己能力慢慢消化，不會被打垮。
  • 容錯：下游短暫故障時，訊息仍保留在 Kafka，恢復後可繼續讀。
  • 可重播：新接入的分析系統，可以從頭重讀歷史事件。
對比其他訊息系統：RabbitMQ 等傳統 MQ 偏向「智慧 Broker、訊息讀完即刪」； Kafka 偏向「簡單 Broker、訊息持久保留、由 Consumer 自己記錄讀到哪」，因此特別適合高吞吐與資料可重播的場景。

術語說明
Broker一台 Kafka 伺服器（節點）。多個 Broker 組成 Cluster（叢集），共同分擔資料儲存與讀寫。
Topic訊息的「類別／主題」，是邏輯上的分類。例如 orders、payments。Producer 寫到某 Topic，Consumer 從某 Topic 讀。
Partition（分區）Topic 在物理上被切成多個 Partition，每個 Partition 是一個有序、僅可追加（append-only）的 log。分區是 Kafka 平行處理與擴展的關鍵單位。

Producer生產者，負責把訊息發布到 Topic。
Consumer消費者，負責從 Topic 讀取訊息。Kafka 採拉取（pull）模型，由 Consumer 主動向 Broker 要資料。
Consumer Group一組共同消費同一 Topic 的 Consumer。組內每個 Partition 只會被一個成員消費，藉此達到負載分攤。
Replica（副本）每個 Partition 可有多份副本，分散在不同 Broker。其中一份是 Leader（處理讀寫），其餘是 Follower（同步備援）。
Controller負責叢集 metadata 管理與 Leader 選舉。舊版依賴 ZooKeeper，新版改用內建的 KRaft（Raft 共識）。
ZooKeeper 還是 KRaft？ Kafka 2.8 起引入 KRaft 模式以移除對 ZooKeeper 的依賴， 3.x 逐步成熟並成為新部署的建議，Kafka 4.0 已完全移除 ZooKeeper。新專案直接用 KRaft 即可。

4. Topic、Partition 與 Offset

這是 Kafka 最核心、也最常被誤解的部分。一個 Topic 由多個 Partition 組成； 每個 Partition 都是一條獨立的「日誌」，新訊息只會被追加到尾端，並分配一個遞增的 Offset。

Partition 就是一條 append-only 的日誌

Partition 0 012 345 ← Producer 從尾端追加新訊息
Partition 1 012 3 ← 各 Partition 的 Offset 各自獨立計算
Partition 2 012 34
已寫入的訊息（數字＝Offset） 最新追加的訊息

幾個關鍵性質：

  • Offset 是「分區內」的編號：Partition 0 的 offset 5 和 Partition 1 的 offset 5 是完全不同的兩筆訊息。
  • 訊息不可變：寫入後不能修改，只能等過期被清掉（retention）。
  • 讀取不刪除：Consumer 讀過的訊息仍留在 log 中，所以可以重播。

順序保證：只在單一 Partition 內成立

非常重要：Kafka 只保證「同一個 Partition 內」的訊息順序， 不保證跨 Partition 的全域順序。如果你的業務要求某類訊息嚴格有序（例如同一帳戶的交易）， 就必須讓這些訊息進到同一個 Partition——做法是給它們相同的 Key（見下一節）。

為什麼要分區？

  • 水平擴展：不同 Partition 可放在不同 Broker，分攤儲存與流量。
  • 平行消費：一個 Consumer Group 內，最多可有「Partition 數量」個 Consumer 同時並行讀取。
    ⇒ Partition 數＝消費端並行度的上限。
分區數怎麼抓？ 太少會限制吞吐與並行度；太多會增加開銷（檔案數、rebalance 時間、端到端延遲）。 常見做法是依目標吞吐量估算，並預留成長空間。注意：Partition 數量只能增加、不能減少。

5. Producer 運作機制

Producer 把訊息送出時，最關鍵的兩個決策是：這筆訊息要進哪個 Partition？以及要等多嚴格的確認？

分區策略：Key 決定一切

flowchart TB S["Producer 送出一筆訊息"] --> Q{"訊息有指定 Key 嗎？"} Q -->|"有 Key"| H["計算 hash(Key) % 分區數"] H --> R["固定送往同一個 Partition
→ 同一 Key 的訊息嚴格有序"] Q -->|"沒有 Key"| RR["Sticky / Round-robin
平均分散到各 Partition
→ 吞吐最大化，但不保證跨分區順序"]
圖 5-1　Producer 分區策略：有沒有 Key 是關鍵分水嶺
  • 指定 Key（例如 user-123）：相同 Key 一定落在同一 Partition，因此該 Key 的訊息順序被保證。適合需要有序的場景。
  • 不指定 Key：Kafka 用 Sticky Partitioning（新版預設）儘量塞滿同一批次再換分區，達到最佳吞吐。
Key 選擇要小心熱點：若某個 Key（例如某大客戶）流量特別大，會造成該 Partition 變成熱點、負載不均。設計 Key 時要兼顧「順序需求」與「分佈均勻」。

寫入確認機制：acks

Producer 送出後要不要等 Broker 確認、等到什麼程度，由 acks 參數決定，這直接影響可靠性與效能的取捨。

sequenceDiagram participant P as Producer participant L as Leader 副本 participant F1 as Follower 1 participant F2 as Follower 2 P->>L: 1. 送出訊息 L->>L: 2. 寫入本地 log L->>F1: 3. 同步複製 L->>F2: 3. 同步複製 F1-->>L: 4. 已同步 F2-->>L: 4. 已同步 L-->>P: 5. 回傳 ack Note over P,F2: acks=0 不等；acks=1 等步驟2；acks=all 等步驟4 全部 ISR 同步
圖 5-2　acks=all 時，Leader 要等所有同步副本（ISR）都複製完才回 ack
acks行為可靠性 / 效能
0送出就不管，不等任何確認最快，但可能丟訊息
1等 Leader 寫入本地 log 即回折衷；Leader 在副本同步前掛掉仍可能丟
all / -1等所有 ISR 都同步完才回最可靠（搭配 min.insync.replicas），延遲較高

批次與冪等性

  • 批次（Batching）：Producer 會把多筆訊息累積成一批再送（受 batch.size、linger.ms 控制），大幅提升吞吐。
  • 冪等性（enable.idempotence=true）：避免因重試造成的重複寫入，讓「同一筆訊息」在 Partition 內只會出現一次。新版 Producer 預設開啟。
  • 交易（Transactions）：跨多個 Partition 的原子寫入，是達成 Exactly-once 的基礎（見第 8 節）。

6. Consumer 與 Consumer Group

Consumer 採拉取（pull）模型：不斷呼叫 poll() 向 Broker 要新訊息。 多個 Consumer 可組成一個 Consumer Group 來分攤同一個 Topic 的負載。

核心規則：一個 Partition 在組內只給一個 Consumer

graph TB subgraph T["Topic: orders（3 個 Partition）"] P0["Partition 0"] P1["Partition 1"] P2["Partition 2"] end subgraph G["Consumer Group: billing"] C1["Consumer A"] C2["Consumer B"] end P0 --> C1 P1 --> C1 P2 --> C2
圖 6-1　3 個 Partition 分給 2 個 Consumer：A 拿到 0、1，B 拿到 2

由此推出幾個重要結論：

  • 組內 Consumer 數 ≤ Partition 數 才能充分平行；多出來的 Consumer 會閒置。
  • 想提高消費並行度，要先增加 Partition 數。
  • 不同的 Consumer Group 彼此獨立：同一筆訊息會被「每個 group」各自完整消費一次（這就是 Pub/Sub 廣播）。

多個 Consumer Group：廣播效果

graph LR K[("Topic: orders")] K --> G1["Group: billing
(計費)"] K --> G2["Group: analytics
(分析)"] K --> G3["Group: notify
(通知)"]
圖 6-2　每個 Group 都能完整讀到全部訊息，各自維護自己的進度

Offset 提交：記錄「我讀到哪了」

Consumer 把處理進度（Offset）提交（commit）到 Kafka 內部一個特殊 Topic __consumer_offsets。 下次重啟或 rebalance 後，就從上次 commit 的位置繼續讀。

  • 自動提交（enable.auto.commit=true）：每隔一段時間自動 commit，方便但可能在「已 commit、未處理完」時丟訊息。
  • 手動提交（false）：自己控制在處理完之後才 commit，可靠性更高（見第 8 節傳遞語意）。
  • auto.offset.reset：當這個 group 沒有已存的 offset 時要從哪開始——earliest（從頭）或 latest（只讀新的）。

Rebalance：成員變動時重新分配

當 Group 有 Consumer 加入／離開，或 Partition 數量改變時，Kafka 會觸發 Rebalance，重新把 Partition 分配給現有成員。

stateDiagram-v2 Stable: 穩定運作 Rebalancing: 重新平衡中 [*] --> Stable Stable --> Rebalancing: Consumer 加入或離開 Rebalancing --> Stable: 重新分配 Partition 完成 Stable --> Rebalancing: Partition 數量改變
圖 6-3　Rebalance 狀態轉換：期間消費會短暫暫停
Rebalance 不是免費的：過程中整個 Group 的消費會短暫停止（Stop-the-world，新版有 Cooperative 漸進式 rebalance 改善）。 頻繁的 rebalance（例如處理太慢導致被踢出 group）會嚴重影響吞吐，要透過調整 max.poll.interval.ms、session.timeout.ms 等避免。

7. Replication 與高可用

為了避免單一 Broker 故障就遺失資料，每個 Partition 可以有多份副本（Replica）， 由 replication.factor 設定（例如 3）。副本分散在不同 Broker 上。

Leader 與 Follower

Leader"] end subgraph B2["Broker 2"] F1["Partition 0
Follower"] end subgraph B3["Broker 3"] F2["Partition 0
Follower"] end L -->|複製| F1 L -->|複製| F2
圖 7-1　每個 Partition 有一個 Leader 處理所有讀寫，Follower 持續同步
  • 同一 Partition 的所有讀寫都只經過 Leader；Follower 只負責同步資料、隨時待命。
  • 不同 Partition 的 Leader 會分散在不同 Broker 上，達到負載平衡。

ISR（In-Sync Replicas）與容錯

ISR 是「目前與 Leader 保持同步」的副本集合。當 Leader 故障時，Kafka 會從 ISR 中選出新的 Leader，服務不中斷。

flowchart TB D["Leader Broker 故障"] --> C["Controller 偵測到"] C --> E{"ISR 中還有副本嗎？"} E -->|"有"| N["從 ISR 選出新 Leader
→ 服務繼續，資料不丟"] E -->|"沒有"| U["視設定而定：
等待 / 或啟用 unclean 選舉（可能丟資料）"]
圖 7-2　Leader 故障後的自動故障轉移（failover）流程
不丟資料的黃金組合：Producer 設 acks=all ＋ Topic 設 replication.factor=3 ＋ min.insync.replicas=2。 意思是「至少要有 2 份副本同步成功才算寫入成功」，即使掛掉 1 台 Broker 仍能正常運作且不丟資料。

8. 訊息傳遞語意

「一筆訊息會被處理幾次」是分散式系統的經典問題。Kafka 支援三種傳遞語意，取捨在於可靠性 vs 效能 vs 複雜度。

flowchart TB Q1{"可以容忍偶爾漏掉訊息嗎？"} Q1 -->|"可以（重效能）"| AMO["At-most-once 至多一次
先 commit offset，再處理
處理失敗就漏掉，不重複"] Q1 -->|"不行（不能漏）"| Q2{"可以容忍重複處理嗎？"} Q2 -->|"可以（最常見）"| ALO["At-least-once 至少一次
先處理，再 commit offset
當機重試會重複 → 下游需冪等"] Q2 -->|"不行（要剛好一次）"| EOS["Exactly-once 精準一次
冪等 Producer + 交易
最嚴格，設定較複雜"]
圖 8-1　依業務需求選擇傳遞語意的決策樹
語意實作關鍵結果適用場景
At-most-once
至多一次		讀到就先 commit，再處理可能漏、不會重複可容忍少量遺失的指標、監控
At-least-once
至少一次		處理完才 commit（手動 commit）不會漏、可能重複最常見；搭配下游冪等處理
Exactly-once
精準一次		冪等 Producer ＋ 交易（read-process-write）不漏不重金流、計費等不容許誤差
實務建議：多數系統選擇 At-least-once + 下游冪等——也就是讓你的處理邏輯「重複執行結果也一樣」 （例如用訊息唯一 ID 去重、用 UPSERT 取代 INSERT）。這比直接上 Exactly-once 簡單可靠許多。

9. 資料保留與 Log Compaction

訊息不會永遠堆著，Kafka 提供兩種清理策略（cleanup.policy）：

① delete：依時間或大小刪除（預設）

  • log.retention.hours：保留時間，預設 168 小時（7 天）。
  • log.retention.bytes：每個 Partition 的大小上限。
  • 超過門檻的舊訊息（整段 segment）會被刪除，與有沒有被消費過無關。

② compact：只保留每個 Key 的最新值

壓縮前 A=1B=1A=2 C=1A=3B=2
壓縮後 C=1A=3B=2 ← 每個 Key 只留最後一筆

Log Compaction 適合「狀態快照」類的資料——你只在乎每個 Key 的最新狀態，不需要完整歷史。 典型用途是 Kafka 內部的 __consumer_offsets、以及 Kafka Streams 的狀態 changelog。

怎麼選？ 事件流（如點擊、交易紀錄）用 delete； 「最新狀態表」（如使用者目前的設定、商品目前的價格）用 compact。

10. 安裝與啟動（KRaft 模式）動手做

以下示範 Kafka 3.x 用內建 KRaft 模式啟動單機環境（不需要 ZooKeeper）。先到官網下載並解壓 Kafka，進入目錄後：

# 1) 產生一個唯一的 Cluster ID
KAFKA_CLUSTER_ID="$(bin/kafka-storage.sh random-uuid)"

# 2) 用該 ID 格式化儲存目錄
bin/kafka-storage.sh format -t $KAFKA_CLUSTER_ID -c config/kraft/server.properties

# 3) 啟動 Broker
bin/kafka-server-start.sh config/kraft/server.properties
Windows 使用者：把上面的 bin/xxx.sh 換成 bin\windows\xxx.bat 即可，例如 bin\windows\kafka-server-start.bat。

更省事：用 Docker

# 拉起官方 Kafka 映像（KRaft 單機）
docker run -d --name kafka -p 9092:9092 apache/kafka:latest

# 進到容器內就能用 CLI 工具
docker exec -it kafka /bin/bash

11. CLI 常用指令

Kafka 內附的命令列工具放在 bin/ 下，最常用的幾個（注意新版統一用 --bootstrap-server）：

建立 / 查看 Topic

# 建立 topic：3 個分區、複本數 3
bin/kafka-topics.sh --create \
  --topic orders \
  --bootstrap-server localhost:9092 \
  --partitions 3 \
  --replication-factor 3

# 列出所有 topic
bin/kafka-topics.sh --list --bootstrap-server localhost:9092

# 查看 topic 詳情（分區、Leader、ISR）
bin/kafka-topics.sh --describe --topic orders --bootstrap-server localhost:9092

收發訊息（測試用）

# 啟動 console producer，之後每行輸入就是一筆訊息

監控 Consumer Group（看 lag）

# 查看某個 group 各分區的 offset 與 lag（落後量）
bin/kafka-consumer-groups.sh --describe --group billing-group \
  --bootstrap-server localhost:9092
Lag（落後量）＝ Partition 的最新 offset − Consumer 已 commit 的 offset。 Lag 持續變大代表消費速度跟不上生產速度，是最重要的健康指標之一。

12. 程式範例（Java / Python）

Java：Producer

import org.apache.kafka.clients.producer.*;
import java.util.Properties;

public class SimpleProducer {
  public static void main(String[] args) {
    Properties props = new Properties();
    props.put("bootstrap.servers", "localhost:9092");
    props.put("key.serializer", "org.apache.kafka.common.serialization.StringSerializer");
    props.put("value.serializer", "org.apache.kafka.common.serialization.StringSerializer");
    props.put("acks", "all");                 // 等所有 ISR 確認，最可靠
    props.put("enable.idempotence", "true");  // 開啟冪等，避免重複寫入

    Producer<String, String> producer = new KafkaProducer<>(props);
    for (int i = 0; i < 10; i++) {
      // 用 key（user-i）決定分區，保證同一 user 的訊息有序
      ProducerRecord<String, String> record =
          new ProducerRecord<>("orders", "user-" + i, "金額:" + (i * 100));

      producer.send(record, (metadata, ex) -> {
        if (ex == null)
          System.out.printf("送達 partition=%d offset=%d%n",
              metadata.partition(), metadata.offset());
        else
          ex.printStackTrace();
      });
    }
    producer.flush();   // 確保緩衝區的訊息都送出
    producer.close();
  }
}

Java：Consumer

import org.apache.kafka.clients.consumer.*;
import java.time.Duration;
import java.util.*;

public class SimpleConsumer {
  public static void main(String[] args) {
    Properties props = new Properties();
    props.put("bootstrap.servers", "localhost:9092");
    props.put("group.id", "billing-group");       // 同 group 共享分區
    props.put("key.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");
    props.put("value.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");
    props.put("auto.offset.reset", "earliest");    // 沒 offset 時從頭讀
    props.put("enable.auto.commit", "false");     // 改手動 commit，更可靠

    KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props);
    consumer.subscribe(Collections.singletonList("orders"));

    while (true) {
      ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
      for (ConsumerRecord<String, String> r : records) {
        System.out.printf("收到 key=%s value=%s partition=%d offset=%d%n",
            r.key(), r.value(), r.partition(), r.offset());
      }
      consumer.commitSync();   // 全部處理完才提交 offset（at-least-once）
    }
  }
}

Python：Producer（confluent-kafka）

from confluent_kafka import Producer

producer = Producer({'bootstrap.servers': 'localhost:9092'})

def delivery_report(err, msg):
    if err:
        print(f'送出失敗: {err}')
    else:
        print(f'送達 {msg.topic()} [{msg.partition()}] offset {msg.offset()}')

for i in range(10):
    producer.produce('orders', key=f'user-{i}',
                     value=f'金額:{i*100}', callback=delivery_report)

producer.flush()   # 送出緩衝區所有訊息

Python：Consumer（confluent-kafka）

from confluent_kafka import Consumer

consumer = Consumer({
    'bootstrap.servers': 'localhost:9092',
    'group.id': 'billing-group',
    'auto.offset.reset': 'earliest',
    'enable.auto.commit': False,   # 手動 commit
})
consumer.subscribe(['orders'])

try:
    while True:
        msg = consumer.poll(1.0)         # 最多等 1 秒
        if msg is None:
            continue
        if msg.error():
            print(f'錯誤: {msg.error()}')
            continue
        print(f'收到 key={msg.key()} value={msg.value().decode()} '
              f'partition={msg.partition()} offset={msg.offset()}')
        consumer.commit(msg)              # 處理完才提交
finally:
    consumer.close()

13. 最佳實踐與常見陷阱

✅ 建議做法

  • 可靠性組合：acks=all ＋ replication.factor=3 ＋ min.insync.replicas=2。
  • 需要順序的訊息一律帶相同 Key。
  • 用手動 commit，並在處理完成後才提交。
  • 下游處理保持冪等（用唯一 ID 去重、UPSERT）。
  • 持續監控 Consumer Lag 與 ISR 數量。
  • 用 Schema Registry（Avro/Protobuf）管理訊息結構演進。
  • Partition 數預留成長空間，一開始就估好。

⚠️ 常見陷阱

  • 以為「全 Topic 有序」——其實只在單一 Partition 內有序。
  • Consumer 數量開超過 Partition 數，多的白白閒置。
  • 處理太慢超過 max.poll.interval.ms，被踢出 group 引發rebalance 風暴。
  • 用 acks=1 卻期待絕不丟訊息。
  • 忘記 Partition 數只能增不能減。
  • 把 Kafka 當資料庫做隨機查詢（它擅長的是順序讀寫的串流）。
  • at-least-once 下未做去重，導致下游重複處理。
